# Milestone 3 — Legal PDF + Public Verification API

This note documents the design decisions and trade-offs of the work delivered for Milestone 3.

## Scope delivered

- Court-ready PDF report generator (`packages/pdf`) with i18n message catalogs in **PT-BR / EN-US / ES-ES**.
- Cover page with metadata, chain status, and a QR code linking to the public verification URL.
- Per-event detail page with `payloadHash`, `chainHash`, and embedded RFC 3161 timestamp metadata.
- Verification instructions page that explains how a reader can recompute the chain hash by hand or via the public API.
- Standalone verification engine (`packages/verify`) + CLI: parses a canonical evidence envelope, recomputes hashes, validates TSA tokens via injected providers, returns a structured pass/fail report.
- Authenticated PDF generation endpoint `POST /v1/reports` returning a streamed PDF with `X-Evidence-Report-*` headers.
- **Public, unauthenticated, rate-limited** endpoints under `/public/...`:
  - `GET /public/v1/evidence/:id` — fetch the canonical envelope by event id (no auth).
  - `POST /public/v1/verify` — verify an envelope independently and get a structured result.
  - `GET /public/verify?event=:id` — human-readable HTML verification page (for the QR code on the PDF).
- OpenAPI 3.1 spec auto-generated by Fastify; interactive Swagger UI at `/docs`.
- Friendly JSON root response at `/` so visitors no longer see a bare 404.

## Key design decisions

### Canonical PDF, byte-stable for the same input

The report is built deterministically: timestamps come from the input (`generatedAt`), not from `Date.now()`. The PDF info dictionary's `CreationDate` and `ModDate` come from the same input. Same input means same output, including same SHA-256, which is the property a future verifier can use to confirm a downloaded PDF hasn't been altered.

### Locale picks the message catalog, jurisdiction picks the TSA hint

Three catalogs live in `packages/pdf/src/i18n.ts`. `resolveLocale()` accepts a loose string (`pt`, `pt-BR`, `PT_BR`, …) and normalizes to one of three canonical values. The same `locale → jurisdiction` mapping from `packages/tsa` is reused so the PDF agrees with whichever TSA stamped the events.

### Public endpoints under a separate rate-limited scope

`@fastify/rate-limit` is registered inside an encapsulated Fastify scope so it only applies to `/public/*` routes. The authenticated `/v1/*` routes are unaffected, which is correct: API consumers shouldn't share a rate budget with random unauthenticated visitors. Default is 60 req/min/IP, configurable via `PUBLIC_RATE_LIMIT_MAX` and `PUBLIC_RATE_LIMIT_WINDOW`.

### Verification is provider-injected

`Verifier` accepts a list of `TSAProvider`s. Each timestamp in an envelope is matched against the registered provider by `id` and verified via `provider.verifyToken()`. If a provider isn't registered for that id, the timestamp is reported as `no-verifier-available` (warning, not failure). This means the verifier never blindly trusts a timestamp it can't independently check, and operators can extend support by adding a provider.

### Human-readable QR landing page

The QR code on every PDF resolves to `/public/verify?event=<id>`, which renders a minimal HTML page with a clear "✓ VERIFIED" or "✗ NOT VERIFIED" banner. This is the path a lawyer or perito who scans the QR with a phone will land on — the JSON `POST /public/v1/verify` endpoint is for programmatic consumers.

### Swagger UI as the developer-facing UX for M1/M2/M3

The implementation prompt deferred a "real" interactive UI to M4. Swagger UI at `/docs` is a respectable interim: every endpoint, every input, "Try it out" buttons, fully browser-friendly, no extra dependencies on the consumer side. Useful for the client's review team during code review.

## What's intentionally not here

- **Full RFC 3161 ASN.1 verification with cert chain validation.** The `Verifier` validates the digest, calls each provider's `verifyToken()`, and surfaces "no-verifier-available" when needed. Production-grade ASN.1 verification belongs in the real TSA providers (ICP-Brasil etc.) once their accredited credentials are wired in.
- **PAdES PDF signing.** The PDF currently has its own SHA-256 in the response header, which is sufficient for chain-of-custody purposes. PAdES-style PKCS7 signing inside the PDF is a v2 enhancement.
- **Offline PDF verification CLI.** The `evidence-verify` CLI parses envelopes (JSON), not PDFs. Adding PDF parsing is a follow-up; for now an offline verifier downloads the envelope via `GET /public/v1/evidence/:id` and feeds it to the CLI.

## Known follow-ups

- `cert_chain` column on `event_timestamps` to store the TSA's certificate chain, used by real ASN.1 verification.
- PDF parsing in the `evidence-verify` CLI so a verifier can `evidence-verify report.pdf` without going to the API.
- Webhook to a tenant-configured endpoint when verification fails (useful for monitoring).
