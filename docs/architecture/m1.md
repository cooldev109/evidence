# Milestone 1 — Event Capture & Hash Chaining

This note documents the design decisions and trade-offs of the work delivered for Milestone 1.

## Scope delivered

- Multi-tenant data model (tenants, API keys, events, per-tenant chain tip).
- Tenant-scoped API key authentication.
- REST API for event ingestion (`POST /v1/events`) with SHA-256 payload hashing and per-tenant hash-linked chain.
- Webhook receiver (`POST /v1/webhooks/:source`) with HMAC-SHA256 signature verification.
- Paginated event read API (`GET /v1/events`, `GET /v1/events/:id`).
- Chain range and verification API (`GET /v1/chain`, `GET /v1/verify`).
- Row-Level Security policies enforcing tenant isolation at the database layer.
- Concurrency-safe chain append via `SELECT ... FOR UPDATE` on per-tenant tip row.

## Key design decisions

### Per-tenant chain tip table

A separate `tenant_chain_tips` row per tenant holds the current `(seq, chain_hash)`. Every append takes `SELECT ... FOR UPDATE` on this row inside a transaction. This serializes appends per tenant — concurrent writers wait for the lock — which is what prevents chain forks under contention.

The trade-off is per-tenant write throughput is bounded by the duration of a single append transaction. For typical chain-of-custody workloads (audit events, document events) this is acceptable. If a tenant ever needs very high write rates, the model can evolve to multiple parallel chains per tenant with a tenant-level merkle root, but that's out of scope for v1.

### Application-generated ISO timestamps stored as TEXT

The chain hash includes `createdAt`. To make verification reproducible, the timestamp string used to compute the hash must round-trip exactly through Postgres. Postgres `timestamptz` normalizes formatting (`2026-05-17T23:24:07.123Z` → `2026-05-17 23:24:07.123+00`), so a `Date → ISO string` round-trip is lossy unless we control both ends.

Decision: `created_at` is a `text` column storing an application-generated ISO-8601 UTC string at millisecond precision. The application owns timestamp generation, so we lose nothing by not letting Postgres parse/format. Range queries by time use string ordering (lexicographic ordering of ISO-8601 timestamps matches chronological ordering when the format is fixed).

### Canonical JSON for payload hashing

`hashPayload(payload)` recursively sorts object keys before JSON-serializing, so `{a:1,b:2}` and `{b:2,a:1}` produce the same hash. This matters because a verifier may reconstruct the payload from any equivalent JSON representation.

### Row-Level Security

`events`, `api_keys`, and `tenant_chain_tips` have RLS enabled with policies that compare `tenant_id` against the connection setting `evidence.tenant_id`. Every tenant-scoped request enters a transaction that runs `SELECT set_config('evidence.tenant_id', $1, true)` first. This is defense-in-depth on top of application-level tenant scoping.

A future improvement: separate database role for the API process so RLS cannot be bypassed even by a SQL-injection bug elsewhere in the codebase.

### Idempotency via `external_id`

Events from webhooks (or any source) can include an `externalId`. The unique index `(tenant_id, source, external_id)` enforces at-most-once delivery; a retry returns the existing event with `idempotent: true` and HTTP 200.

### API key storage

Keys are issued with the prefix `evk_` and stored in the DB only as `SHA-256(plaintext)`. The plaintext is shown to the operator once at creation time and never persisted. Lookup is a single indexed equality match on the hash column.

## Acceptance criteria — coverage

| Criterion | Status | Where it's exercised |
|-----------|--------|----------------------|
| Events ingested via REST + webhook with auth and tenant scoping | ✓ | `apps/api/test/capture.test.ts` |
| SHA-256 payload hash + hash-linked chain | ✓ | `packages/core/src/chain.test.ts`, integration tests |
| Concurrent inserts cannot fork the chain | ✓ | "chain integrity under concurrency" — 50 parallel appends |
| `verifyChain` detects tampering or gaps | ✓ | unit + integration ("detects tampering when an event payload is mutated in the DB") |
| CI green, ≥ 80% coverage on `packages/core` | ✓ | 15 unit tests across hash + chain; CI in `.github/workflows/ci.yml` |

## What's intentionally not here

- TSA timestamping — Milestone 2.
- S3 evidence storage — Milestone 2.
- KMS encryption — Milestone 2.
- Per-tenant retention configuration — Milestone 2.
- Admin UI — Milestone 4.
- Public verification API — Milestone 3.

## Known follow-ups

- Add `pino` request logging middleware with `tenant_id`/`request_id` propagation (currently logs at server level only).
- Rate limiting per API key (Fastify rate-limit plugin, scoped by `tenant_id`).
- A dedicated lower-privilege Postgres role for the API process to harden RLS.
