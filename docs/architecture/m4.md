# Milestone 4 — Multi-Tenant React Admin Panel

Design decisions and trade-offs for the final milestone.

## Scope delivered

- **Admin backend** (the API had no admin surface before — only tenant API-key auth):
  - `admin_users` table (email + scrypt password hash, scoped to a tenant) and `audit_events` table (migration 0003), both under tenant RLS.
  - `POST /admin/v1/login` → HS256 JWT (12 h TTL) carrying `{ sub, tid, email }`.
  - JWT-guarded admin API: `/admin/v1/me`, `/overview`, `/events`, `/events/:id`, `/verify`, `/api-keys` (list/create/revoke), `/reports`, `/settings` (get/patch), `/audit`.
  - Every mutating admin action is written to the audit log (`login`, `api_key.create`, `api_key.revoke`, `report.generate`, `settings.update`).
  - `admin:create-user` CLI to bootstrap operators (no public signup).
- **React admin SPA** (`apps/admin`): Vite + React 18 + TypeScript + react-intl.
  - Screens: Login, Dashboard, Events (+ detail), Reports (PDF export), API keys, Settings, Audit.
  - Full **i18n in PT-BR / EN-US / ES-ES** with a locale switcher; default locale seeded from the tenant.
  - Served by the API at `/app` via `@fastify/static`; built into the Docker image in a dedicated stage.

## Key design decisions

### Admin users belong to a tenant

Each admin user is scoped to one tenant (`admin_users.tenant_id`). The JWT carries that tenant id, and every admin endpoint reads only that tenant's data. This is the standard multi-tenant SaaS model: a customer's operators manage their own evidence, nothing else. A platform-wide super-admin role can be layered on later without changing this.

### Separate auth surface from the ingestion API

The existing `/v1/*` endpoints authenticate with a tenant **API key** (`Bearer evk_...`) — those are for the tenant's own systems pushing events. The admin panel is a different consumer (a human operator), so it gets a separate `/admin/v1/*` surface authenticated by a **JWT** from email/password login. Keeping them separate means an admin session can't be used to forge events and an API key can't reach admin operations.

### Hand-rolled HS256 JWT, scrypt passwords — no native deps

JWT signing/verification is a small HMAC-SHA256 implementation over Node's `crypto` (`src/auth/jwt.ts`); passwords use Node's built-in `scrypt` (`src/auth/password.ts`). This avoids native build dependencies (bcrypt) and external JWT libraries, keeping the image simple. For higher-security deployments these can be swapped for argon2 + a vetted JWT lib without changing call sites.

### SPA served by the API, HashRouter

The built SPA is served at `/app` by the API (`@fastify/static`), so the deployment stays a single origin and Caddy needs no static-file config — it just proxies everything to the API. The SPA uses **HashRouter**, so all client routes live under `/app/#/...` and resolve to one `index.html` — no server-side SPA-fallback rules needed. API calls go to `/admin/v1/*` and `/v1/*` on the same origin (no CORS).

### Docker: dedicated admin-build stage

The image builds the SPA in an `admin-build` stage (`pnpm --filter @evidence/admin build`) and copies only the resulting `dist` into the runtime image. Source and dev tooling for the SPA never reach the final image.

## What's intentionally not here

- **Public self-signup / password reset** — operators are provisioned with the `admin:create-user` CLI for v1.
- **Roles/permissions beyond `admin`** — the `role` column exists; RBAC is a later refinement.
- **Event filters (date/source/search) in the UI** — list + pagination + detail are in; richer filters are a follow-up (the API already supports cursor pagination).
- **Tenant creation from the UI** — still CLI/SQL (platform-operator concern, not a tenant-operator one).

## Known follow-ups

- Argon2 + audited JWT lib if the threat model warrants.
- The standing RLS-owner-bypass hardening (app connects as table owner) applies to the admin tables too; isolation is currently enforced by query scoping + JWT tenant binding.
- Add a "verification dashboard" detail view (per-event TSA status, retention summary) beyond the current chain-health badge.
