# Milestone 2 — TSA Timestamping & Append-Only Storage

This note documents the design decisions and trade-offs of the work delivered for Milestone 2.

## Scope delivered

- Provider-agnostic RFC 3161 Timestamp Authority abstraction (`packages/tsa`).
- `MockTSAProvider` — deterministic, in-memory, used in tests and dev.
- `FreeTSAProvider` — real RFC 3161 HTTP client targeting [freetsa.org](https://freetsa.org).
- Stub providers for ICP-Brasil, eIDAS, and US-DigiCert that error politely until credentials are wired in.
- Locale-driven provider selection (`pt-BR` → BR, `en-US` → US, `es-ES`/`de-DE` → EU, default → DEV).
- Append-only evidence storage abstraction (`packages/storage`).
- `LocalFilesystemStore` — writes evidence with POSIX read-only perms + a sidecar retention manifest; rejects overwrites.
- `S3ObjectLockStore` — AWS SDK + Object Lock retention + KMS server-side encryption.
- Canonical evidence envelope: JSON with sorted keys so the byte stream is reproducible.
- `EvidencePersistenceService` — coordinates the TSA + storage pipeline after every event capture.
- Database additions: `event_timestamps`, `evidence_objects`, `tenant_settings`, all under RLS.
- `GET /v1/events/:id/evidence` returns the canonical envelope with `X-Evidence-Sha256` / `X-Evidence-Object-Key` / `X-Evidence-Stored-At` headers.

## Key design decisions

### Provider-agnostic TSA layer

`TSAProvider` is a tiny interface: `requestToken(digestHex)` returns a `TimestampToken` with the RFC 3161 token bytes, the issued-at, the digest, and the provider id. `verifyToken(token, expectedDigestHex)` returns a structured pass/fail. Adding a new TSA is a single file that implements this interface.

The mock provider lets us write tests that don't depend on the public internet. The real `FreeTSAProvider` is built and ready to use against `https://freetsa.org/tsr` — it just isn't the default in CI to avoid flakiness.

Stub providers (`ICPBrasilProvider`, `EIDASProvider`, `USDigicertProvider`) are concrete classes that throw `TSAError(code='not-configured')` until credentials are wired in. They exist now so the selector logic can route to them and the registration code in `bootstrap.ts` is final; only the network call inside each `requestToken` needs filling in.

### Locale → jurisdiction → provider

`localeToJurisdiction(locale)` maps `pt-BR` → `BR`, `en-US` → `US`, `es-*` / `de-*` etc. → `EU`, others → `DEV`. The registry holds per-jurisdiction defaults (e.g., `BR: 'icp-brasil'`), and `pickProvider({ locale, override })` returns the right provider. An explicit `override` short-circuits the locale routing — useful for re-issuing tokens through a specific provider or for ops debugging.

This means a single deployment can serve PT-BR, EN-US, and ES-ES tenants and pick the right jurisdiction-appropriate TSA per request automatically.

### Pluggable storage with the same shape as S3 Object Lock

`EvidenceStore` exposes only `putEvidence`, `getEvidence`, and `headEvidence`. There is no `delete` method — removal is the underlying store's concern, governed by its retention policy.

`LocalFilesystemStore` simulates Object Lock for dev/CI:
- writes evidence at `<root>/<tenantId>/<eventId>.evd` with mode `0o400`
- writes a sidecar `.retention.json` manifest with `retainUntil` and `retainMode`
- refuses to overwrite an existing key (raises `ImmutabilityViolation`)

This is faithful enough that integration tests can prove the application never overwrites a stored object, without needing LocalStack or a real S3 bucket.

`S3ObjectLockStore` uses `PutObjectCommand` with `ObjectLockMode` (`COMPLIANCE` or `GOVERNANCE`) and `ObjectLockRetainUntilDate` set from the application's retention configuration. KMS server-side encryption is enabled when a key id is configured. The bucket MUST be created with Object Lock enabled at creation time — Terraform under `infra/aws/` (to be added) provisions this.

### Canonical envelope

The evidence envelope written to storage is `canonicalJson(envelope)`:

```json
{
  "version": 1,
  "event": { ... full event row including the original payload ... },
  "timestamps": [
    { "provider": "...", "jurisdiction": "BR", "issuedAt": "...",
      "digestHex": "...", "tokenBase64": "..." }
  ]
}
```

Sorted-key serialization means the envelope's SHA-256 is reproducible: a third party who reconstructs the envelope from its component parts will compute the same hash, which is what makes independent verification (Milestone 3) possible.

### Retention defaults

`RETAIN_MODE` defaults to `governance` and `RETAIN_YEARS` to 5. Production deployments switch `RETAIN_MODE` to `compliance` after explicit sign-off. Per-tenant overrides live in `tenant_settings` (column added in this milestone, UI in Milestone 4).

### Inline persistence vs background job

For this milestone, `appendEvent` is followed synchronously by `persistence.persist()` inside the same request. The TSA call adds ~50–500ms depending on the provider. For latency-sensitive callers we can move this to a background queue (BullMQ or similar) without changing the public API — `persist()` is already idempotent at the storage layer (overwrite is rejected) and at the timestamp layer (unique index on `(event_id, provider)`).

## Acceptance criteria — coverage

| Criterion | Status | Where exercised |
|-----------|--------|-----------------|
| Every event has a valid RFC 3161 timestamp from the locale's provider | ✓ | `apps/api/test/evidence.test.ts` — "persists a TSA timestamp", "locale → jurisdiction" |
| TSA provider swappable without touching capture or storage code | ✓ | `packages/tsa/src/tsa.test.ts` — "provider selector" tests |
| Every event has an immutable S3-style object that cannot be modified before expiry | ✓ | `packages/storage/src/local-store.test.ts` — "rejects attempts to overwrite" |
| Evidence at rest is encrypted with a tenant-scoped KMS key | ✓ (S3 path) | `packages/storage/src/s3-store.ts` — `ServerSideEncryption: 'aws:kms'`, `SSEKMSKeyId` |
| Canonical envelope is reproducible | ✓ | `apps/api/test/evidence.test.ts` — "deterministic (canonical JSON)" |

## What's intentionally not here

- Full RFC 3161 response parsing and cert-chain validation — built in Milestone 3 inside the standalone verifier so that `packages/tsa` stays dependency-light.
- Terraform for the S3 bucket + KMS key + IAM role — added once the client provisions IAM access.
- Background job runner — synchronous persistence is fine at current scale.
- Pulling per-tenant overrides from `tenant_settings` at request time — schema in place, wiring deferred to Milestone 4 (admin UI surfaces these).
- Production TSA credentials for ICP-Brasil / eIDAS / US — stubs in place, plug-in is one file change each.

## Known follow-ups

- Wire `tenant_settings` (per-tenant retention years + tsa override) into the persistence path.
- Move TSA + storage off the synchronous request path once we observe real latency in staging.
- Add an Inspector endpoint that exposes the public verification interface for Milestone 3.
- Add a `cert_chain` column on `event_timestamps` once we start storing TSA response certs (deferred to M3 verifier).
